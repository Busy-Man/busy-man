# pr-commit

**규칙은 `AGENTS.md` §1(파일 소유권)과 §5(커밋과 브랜치)에 있다. 시작할 때 그 파일을 읽는다.**
여기에 규칙을 옮겨 적지 않는다 — 두 벌이 되면 어긋났을 때 어느 쪽이 맞는지 알 수 없다.
여기 있는 것은 **순서**뿐이다.

## 순서

**1. 읽는다**

- `AGENTS.md` §1, §5 — 소유 경계와 `type(scope)` 유효값
- `git status --short --branch`, `git diff`, `git diff --staged`
- `git log --oneline -5` — 이 저장소의 메시지 결이 어떤지

**2. 브랜치를 확인한다**

`main`이면 **멈추고** 브랜치를 먼저 만든다. §5가 main 직접 push를 금지한다.

브랜치가 없으면 작업 성격에 맞는 이름을 제안한다 (`feat/…` `fix/…` `chore/…` `docs/…`).

**3. 소유 경계를 점검한다**

변경된 파일이 `AGENTS.md` §1에서 **다른 사람 담당인지** 본다.
섞여 있으면 커밋하기 전에 알린다.

```
⚠ src/phone.js 는 B 담당입니다. (§1)
  이 변경을 포함할까요, 되돌릴까요?
```

§1은 "고쳐야 할 이유가 생기면 고치지 말고 상대에게 말한다"고 정하고 있다.
자동으로 판단하지 말고 사람에게 묻는다.

`src/state.js`가 섞여 있으면 **접점이 4개를 넘는지** 함께 본다 (§2).

**4. 커밋을 나눈다**

한 커밋 = 한 가지 이유. 되돌릴 때 같이 되돌아가야 하는 것끼리 묶는다.

나눌 후보를 보여주고 확인을 받는다. 파일 하나가 두 목적에 걸치면
그 사실을 말하고 어떻게 할지 묻는다 — 임의로 쪼개지 않는다.

**5. 메시지를 쓴다**

형식과 `scope` 유효값은 §5를 그대로 따른다.

본문은 **"왜"만 2~3줄.** 무엇을 바꿨는지는 diff가 말한다.
바꾼 파일을 나열하거나 변경량을 적지 않는다.

판단이 갈렸던 곳, 대안을 버린 이유, 나중에 다시 논의될 것 같은 곳을 적는다.
그런 게 없는 커밋이면 제목 한 줄로 끝낸다.

**6. PR 본문을 만든다**

`.github/pull_request_template.md`와 **같은 섹션**으로 쓴다. 섹션을 늘리지 않는다.

```
## 개요
왜 이 PR이 필요한지 2~3줄.

## 변경 사항
커밋 단위로. 각 줄에 "무엇을" 말고 "왜"가 보이게.

## 체크리스트
템플릿 항목을 실제로 확인하고 표시한다. 확인 안 한 것을 체크하지 않는다.
```

base 브랜치를 확인한다. 기본은 `main`이다 (§5 — develop을 쓰지 않는다).

## 하지 말 것

- `git add -A` / `git add .` — `.gitignore`가 모든 브랜치에 있지 않다.
  실제로 `.omc/`가 통째로 커밋된 적이 있다. **파일을 명시해 스테이징한다**
- `--amend`로 이미 push된 커밋 고치기, squash, force-push (§5 — 심사 요건)
- 사용자가 요청하지 않은 커밋·push·PR 생성
- 메시지에 검증 로그나 변경 파일 목록 채워 넣기
- 남의 담당 파일을 물어보지 않고 커밋에 포함하기
