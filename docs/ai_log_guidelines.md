# AI 활용 기록 관리 지침

`ai_usage_log.md`를 작성·갱신할 때 사람과 에이전트가 따르는 규칙. 이 문서는 로그의 **작성 방법**만 규정하고, 대회 요건 자체는 `대회_정보.md`를, 게임 기획 내용은 `기획 초안.md`를 기준으로 한다.

실행 절차는 `/ai-log` 스킬(`.claude/skills/ai-log/`)에 있다. 스킬과 이 문서가 어긋나면 **이 문서가 우선이다.**

---

## 0. 왜 이 기록이 필요한가

제출물 4번(AI 활용 기술 문서)은 **AI 도구 · 프롬프트 · 활용 내역**을 요구한다. 이 프로젝트는 게임 내 런타임 AI를 탑재하지 않기로 했으므로, **문서 4번의 내용은 전부 개발 과정 기록에서 나온다.** 기록을 빠뜨리면 쓸 재료가 없다.

그리고 프롬프트와 작업 맥락은 **시간이 지나면 복원이 불가능하다.** 산출물은 저장소에 남지만 "무엇을 어떻게 지시했는지"는 남지 않는다.

### 세 개의 층

| 층 | 위치 | 누가 채우나 | 성격 |
|---|---|---|---|
| 원자재 | `ai-log/raw/YYYY-MM-DD.md` — **저장소 밖(노션)** | **훅이 자동으로** | 프롬프트 원문 + 그 지시가 반영된 커밋. 손대지 않는다 |
| 중간 산출물 | `ai-log/specs/` | 옮겨서 커밋 | AI가 만든 명세·계획서. 생성 당시 그대로 |
| 정식 엔트리 | `ai_usage_log.md` | `/ai-log`가 사람에게 물어서 | 판단이 들어간 기록. 제출물의 재료 |

훅이 잡을 수 있는 것은 원문뿐이다. `사람이 한 것`·`반영` 같은 판단 필드는 사후에만 알 수 있으므로 자동화하지 않는다.

**원자재만 저장소에 두지 않는다.** 제출물 4번의 재료이지 소스가 아니고, 올린 뒤에는 심사 요건(squash·force-push 금지) 때문에 정정할 수 없기 때문이다. 각자 로컬에 쌓이는 것을 **하루 한 번 노션에 수동으로 올리고**, 문서를 쓸 때 내려받는다. 사유 전문과 파일명 규칙은 `ai-log/raw/README.md`에 있다.

**훅은 Claude Code에서만 동작한다.** Codex 등 다른 도구로 작업했다면 그 세션의 원문은 직접 `ai-log/raw/`에 붙여넣는다.

---

## 1. 대원칙 — 넘치게 기록한다

**의심스러우면 남긴다.** 마감 시점에 걸러내는 것은 몇 분이면 되지만, 남기지 않은 것을 되살리는 것은 불가능하다.

- 기존 항목을 지우거나 요약해서 줄이지 않는다. 로그는 **누적 파일**이다.
- 나중에 폐기된 산출물도 지우지 않는다. `반영` 값을 `폐기`로 바꾸고 사유를 적는다.
- 분량이 많아 보인다는 이유로 항목을 합치지 않는다.
- `ai-log/raw/`는 정리하거나 삭제하지 않는다.

---

## 2. 언제 기록하는가

다음 중 하나라도 해당하면 **에이전트가 먼저 로그 갱신을 제안한다.** 사용자가 요청할 때까지 기다리지 않는다.

- AI가 만든 코드·아트·사운드·레벨 데이터·문서가 실제로 프로젝트에 들어갔을 때
- AI 산출물을 사람이 크게 고쳤을 때 (무엇을 왜 고쳤는지가 문서의 핵심 재료)
- AI가 낸 것을 채택하지 않기로 했을 때
- 설계 판단이 바뀌었을 때 (근거가 기록되어야 나중에 같은 논의를 반복하지 않는다)
- 새 AI 도구를 처음 사용했을 때 → §0 도구 목록에도 행 추가
- 외부 에셋·오픈소스를 사용했을 때 → §4 출처 표에 즉시 추가
- AI가 계획·명세 문서를 만들었을 때 → `ai-log/specs/`로 옮긴다. 아래 §4 참조

**기록하지 않아도 되는 것** — 오타 수정, 단순 포맷팅, 한 줄짜리 질의응답, 결과물이 남지 않은 잡담.
다만 애매하면 남긴다. 위 목록은 좁게 해석한다.

## 3. 엔트리 작성 규칙

새 항목은 `L-0NN` 순번으로 §2 끝에 추가하고, §1 색인 표에도 같은 순서로 행을 추가한다. 색인과 본문이 어긋나지 않도록 항상 함께 갱신한다. 파일 상단의 최종 갱신일과 누적 항목 수도 함께 고친다.

각 엔트리는 다음을 반드시 채운다.

| 항목 | 작성 규칙 |
|---|---|
| 날짜 | `YYYY-MM-DD` |
| 영역 | 기획 / 코드 / 아트 / 사운드 / 레벨·밸런싱 / 문서 / 도구·자동화 중 하나 |
| 도구 | 모델·버전까지. "Claude"가 아니라 "Claude Opus 5 (웹 대화)", "Claude Code" 등 |
| 담당 | 팀원 중 누가 지시했는지. 미정이면 `(미정)`으로 두고 역할 분담 확정 시 소급 기입 |
| 목적 | 무엇을 얻으려 했는지 한 줄 |
| 반영 | 그대로 / 부분 수정 / 골격만 차용 / 폐기 |
| 프롬프트 | **원문 우선.** 아래 §4 참조 |
| 산출물 | AI가 실제로 내놓은 것. 파일명이 있으면 파일명, 판단이면 판단 내용을 요약 |
| 사람이 한 것 | **비워두지 않는다.** 발상·결정·수정·검증 중 무엇을 했는지. 제출물 5번(팀원 롤 기술서)의 근거이기도 하다 |

### 영역 분류가 애매할 때

산출물이 최종적으로 어디에 들어갔는지를 기준으로 정한다. 기획 논의 끝에 코드가 나왔다면 `코드`다. 두 영역에 걸치면 엔트리를 둘로 나눈다.

### 반영 값의 뜻

- **그대로** — 거의 손대지 않고 사용
- **부분 수정** — 뼈대는 유지하되 사람이 고쳐서 사용
- **골격만 차용** — 아이디어나 구조만 가져오고 실제 결과물은 다시 만듦
- **폐기** — 사용하지 않음. §3 폐기 표에도 행을 추가하고 사유를 적는다

## 4. 원문과 중간 산출물 취급

### 프롬프트 원문

**요약으로 원문을 대체하지 않는다.** 요건이 요구하는 것은 "AI에게 준 주요 프롬프트·지시 사항"이지 그 요약이 아니다.

- 원문은 `ai-log/raw/YYYY-MM-DD.md`에 이미 쌓여 있다. 여기서 가져온다.
- 짧은 지시(수 문장 이내)는 엔트리 안에 인용 블록으로 그대로 넣는다.
- 긴 세션은 엔트리에 다 옮기지 말고 `ai-log/raw/`의 날짜와 시각으로 가리킨다. 원문은 이미 거기 있다.
- 원문이 길어 요약이 필요하면 **요약과 원문을 병기**한다. 원문을 지우지 않는다.
- 원문을 확보하지 못한 경우, 지어내지 말고 `(원문 미확보 — 요약만)`이라고 명시한다. **소급해서 그럴듯한 프롬프트를 창작하지 않는다.**

### 반영 커밋을 함께 읽는다

raw의 각 항목에는 **그 지시가 반영된 커밋**이 붙어 있다. `git show --stat <해시>`로 실제 산출물을 확인할 수 있으므로, `산출물` 필드를 기억에 의존해 채우지 않아도 된다.

`반영 커밋: _없음_`은 그 턴에 커밋이 없었다는 뜻이다. 논의만 했거나, 결과가 나중 커밋에 섞여 들어갔거나 둘 중 하나다. 후자라면 어느 커밋인지 확인해서 엔트리에 적는다.

### AI가 만든 계획·명세 문서

deep-interview 명세, 계획서, 설계 판단 기록처럼 **코드가 아닌 AI 산출물**은 `ai-log/specs/YYYY-MM-DD-<주제>.md`로 옮겨 커밋한다.

- 에이전트 도구의 작업 디렉터리(`.omc/` 등)는 `.gitignore` 대상이다. **거기 두면 팀원이 볼 수 없고, 정리하는 순간 사라진다.**
- 생성 당시 그대로 옮긴다. 다듬지 않는다.
- 채택되지 않은 안도 남긴다. 잘라낸 이유가 곧 §3 폐기 기록의 재료다.
- 나중에 판단이 바뀌어도 이 파일을 고치지 않는다. 바뀐 내용은 엔트리와 §3에 적는다.

코드는 커밋에 남지만 **"왜 그렇게 만들기로 했는가"는 남지 않는다.** 그것이 남는 곳이 여기다.

## 5. 외부 에셋 출처

에셋을 쓰는 **그 순간** §4 표에 추가한다. 나중에 몰아서 정리하지 않는다.

- 파일 경로 / 종류 / 출처 URL / 라이선스 / 저작자 표기 의무 / 비고를 모두 채운다.
- **라이선스를 확인할 수 없는 에셋은 사용하지 않는다.** 이 원칙은 `대회_정보.md`의 제한사항에서 온 것으로, 협상 대상이 아니다.
- AI로 생성한 에셋도 기록한다. 생성 도구와 프롬프트가 곧 출처다.
- 오픈소스 라이브러리, 폰트, 샘플 코드도 에셋에 포함한다. (three.js를 도입하면 여기에 적는다.)

## 6. 마감 시점의 변환

로그는 그대로 제출하는 문서가 아니다. 마감 전에 아래 목차의 PDF로 재구성한다. 로그 구조는 이 목차를 채우도록 설계되어 있다.

| 문서 4번 절 | 로그에서 가져올 곳 |
|---|---|
| 1. 개요 — 사용 도구와 활용 영역 | §0 도구 목록 + §1 색인의 영역 분포 |
| 2. 개발 과정에서의 AI 활용 (영역별) | §2 엔트리를 영역별로 묶어 서술 + 프롬프트 원문 |
| 3. 게임 내 AI 기능 | §5 미탑재 판단 근거 |
| 4. 외부 에셋·오픈소스 출처 | §4 출처 표 |
| 5. AI 산출물의 검증 | §3 폐기 기록 + 각 엔트리의 "사람이 한 것" |

**분량 감각** — 최종 PDF 3~6쪽. 영역별로 2~4건씩, 총 15~25건 정도가 쌓여 있으면 자연스럽게 채워진다.

**균형 점검** — 개발이 시작된 뒤에도 `기획`·`문서` 영역이 로그의 대부분을 차지하면, 문서 4번이 "AI와 상의해서 만들었다"로 읽힌다. `코드`·`아트`·`사운드`·`레벨·밸런싱` 기록이 절반 이상이 되도록 에이전트가 주기적으로 확인하고, 한쪽으로 쏠리면 알린다.

## 7. 하지 말 것

- 원문을 요약으로 갈음하기
- 확보하지 못한 프롬프트를 그럴듯하게 지어내기
- 폐기된 산출물의 기록을 지우기
- "사람이 한 것"을 빈칸으로 두기
- 에셋을 쓰고 출처 기록을 미루기
- 로그가 길어졌다는 이유로 과거 항목을 압축하기
- 색인만 고치고 본문을 빠뜨리거나, 그 반대로 하기
- `ai-log/raw/`를 정리하거나 삭제하기
